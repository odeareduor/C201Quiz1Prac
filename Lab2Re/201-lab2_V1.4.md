### 1 Getting started

Of course, in a computer we make files, and not food. However, to get an idea of what Make does, suppose that we want to make bibimbap a Korean rice dish with beef. To make bibimbap, we need a set of instructions tellings us what the required ingredients are, and how we should put these ingredients together to produce the nal dish. We write this information in a plaintext file named Makefile . As you saw in lectures, such a file has rules. For example, the Makefile below has has 4 rules:

```
bibimbap : rice beef
   echo " Here is your bibimbap ."
rice :
   echo "Here 's some rice ."
beef : fryingPan sauce
   echo "Here 's some beef "
fryingPan :
   echo "We have a frying pan at this location :"
   pwd
sauce :
   cat sauce .txt
```

What is to the left of each colon is the target of the rule. What follows the colon is a space-separated list of the required ingredients (aka dependencies or prerequisites) to make

the target. For example, to make bibimbap , we need rice and beef . What do we need to make beef ?

Below the colon line, following a tab character, is a Bash command that somehow uses the ingredients and actually produces the target. This Bash command is called the recipe. Needless to say, there is no bibimbap-making Bash command. For this reason the recipes written above are simply print statements to make this example work. Thus we learn that the recipe can be anything, even totally unrelated to the target and the dependencies. Also note that the recipe for fryingPan has 2 Bash commands written on separate lines. These commands will be executed in the written order. Thus we learn a receipe need not necessarily be a single Bash command.

Make normally understands the targets to be files that need to be made. What do you think Make will do if you attempt make bibimbap while there already exists a file named sauce in that directory? Try and observe. You will see that Make is smart in that if there already is sauce in the folder, it does not execute the recipe for sauce . Can you appreciate how benecial this is when our computer project has a big number of files each of which must be separately compiled into machine code?

As you learned in lectures, when a command like make bibimbap is executed, Make goes through a decision tree that makes any target that is directly or indirectly required for bibimbap if it doesn't exist, or remakes it if it is outdated in the sense that a dependency of it has been changed since the target was last made. The algorithm for make bibimbap is something like the following:

- 1. For each dependency x of bibimbap , recursively repeat this algorithm on x .
- 2. After the recursive calls have returned, check if the file bibimbap already exists.
  - If yes, are any of its dependencies newer than it?

If yes, rebuild bibimbap using the recipe.

Otherwise, do nothing.

Or commands.

If no, build bibimbap using the recipe.

The decision tree is in fact more complicated than written above because Make has built-in rules beyond the ones we write in a Makefile. Explaining those rules here confuses more than it helps the objective of this lab. So we ignore them.

#### 5 Phony targets

Writing rules with targets like clean or test are ways for us to automate Bash commands that we want to run without typing the entire command. These rules, unlike the usual rules we have in a Makefile, do not actually produce the target. For example, the rule myProg that you wrote in and will actually produce a file named myProg , but the rule clean in does not produce a file named clean . We call such rules phony. A phony rule must always execute the recipe, even if there happens to be a file that shares the name of the target. Research, or ask your lab instructor, how we can achieve this.

#### 6 Variable in Makeles

Take a look at your Makefile. You will see that many things are repeated multiple times. For example, the compiler command gcc is repeated for every compilation or linking receipe.

If later you want to rebuild this program with a different compiler, say CLang, then all those gccs must be changed to clang. You can see how one may miss one of them or make a typographical error. The easier way is to replace the compiler name in all recipes with a Make variable. The variable name does not matter, but traditionally this variable is called CC for "C compiler". Creating the variable is similar to Python: We simply write CC = gcc on top of the Makefile. Using the variable, however, has a funny syntax. It requires a dollar sign, followed by a pair of parentheses that enclose the variable name. So to use CC you write \$(CC) in your receipe. The variables can be used anywhere and not just within recipes. This includes targets and dependency lists. Another common variable to use in Makefiles is for all the flags we give the compiler. While again the name of the variable does not matter, this variable is traditionally named CFLAGS.

#### 7 Automatic variables in Makefiles

Some variables are built-in for use within recipes, and they have single-character names. These special variables are known as automatic variables [2]. The value of these variables change depending on in which recipe they are used. Since these variable names never have multi-character names, when using these variables we don't enclose the name in parentheses. For example, an automatic variable is the "at" sign @. If in a recipe of a rule we have anywhere, it automatically expands to the name of the target of that rule. The choice of character makes sense too: @ is meant to resemble a shooting target with a bullseye. Analogously, using \$^ in the receipe expands to the entire dependency list because resembles an up arrow  $^$  and the dependency list is above the recipe. Research these automatic variables and learn about more than the two mentioned here.
